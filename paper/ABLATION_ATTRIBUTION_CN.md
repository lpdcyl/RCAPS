# 关键资源反馈的独立作用：给导师的说明

## 为什么原有证据不够

完整 RCAPS 与 Helix 同时改变模型放置和在线调度，所以完整系统的吞吐或时延差异不能直接归因于“关键路径”。已有开发负载的放置内部对照也提示效果具有条件性：三集群从粗布局到关键资源细化，平均吞吐变化约 -0.006%，TTFT 改善约 -0.356%，TPOT 改善约 3.09%。这支持“某些解码瓶颈得到改善”，尚不足以支持“关键路径细化是所有性能提升的主要来源”。

## 嵌套放置消融

我们在同一物理拓扑、24 台异构 GPU、模型、请求轨迹、种子、固定窗口和 **RCAPS 在线调度器** 下，只替换布局生成规则：

| 档位 | 布局生成规则 | 比较回答的问题 |
| --- | --- | --- |
| A：仅容量 | 按显存容量选共享 GPU、平衡两条后缀并分配层；不读取 RTT 和带宽；全部 24 台 GPU 均放置至少一层 | 显存可行的双后缀构造本身表现如何？ |
| B：容量＋拓扑 | A 的容量和结构约束上，加入 RTT 连通分组、源到共享 GPU 的 RTT 以及链路代价引导的设备顺序；不做局部细化 | 拓扑感知初始化相对仅容量增加多少？ |
| C：容量＋拓扑＋关键资源 | 从 B 出发，用事件图估计关键资源，选择相邻边界移动、设备顺序交换和共享前缀调整 | 关键资源反馈在既定拓扑初始化上的**增量**是多少？ |

A、B、C 分别对应 `rcaps_capacity`、`rcaps_coarse` 和正式 RCAPS 布局。三档沿用相同的共享前缀／双后缀结构和合法拼接边导出规则；当前两个拓扑中每档都使用 1 台共享 GPU、两条分别含 11 与 12 台 GPU 的后缀，合计 24 台设备。放置导致共享设备和层区间不同，是这一实验要测的处理变量。

对每个种子先计算 B 相对 A、C 相对 B 的配对差异，再给出三种子的原值、均值、样本标准差和变化范围。吞吐同时报告绝对 token/s 差值及相对比例，P95 延迟报告秒数和相对比例；因为相对比例分母不同，不把两段百分比相加。三档均附到达数、首 token／TPOT 样本数、完成率、窗口末积压，以及双方都观测到的同一请求集合上的 P95。

直接的 B/A 对照由 `python -m benchmarks.compare --main-method rcaps_coarse --baselines rcaps_capacity --seeds 0 1 2` 生成；C/B 对照用 `--baselines rcaps_coarse`。每一对都先检查轨迹哈希和逐请求输入，而不通过两张分别以 Helix 为分母的表间接相减。

## “完整 RCAPS”怎么放在表中

C 已经是最终放置加 RCAPS 调度器，即完整 RCAPS。它不能作为该放置阶梯之外的第四个独立增量。完整 RCAPS 相对 Helix 的结果放在另一张端到端表，说明**联合效果**；现有固定放置的调度对照另列，说明该特定布局和负载下的调度作用。官方高负载上 Helix 调度与新放置的组合曾出现不可路由失败，所以不能假设一个完整的放置×调度二因素表已经得到验证。

## 结论如何随数据调整

- 若 B 明显优于 A，而 C 与 B 接近：主贡献表述应落在拓扑感知的容量可行路径构造及在线资源感知调度；事件图用于定位与解释瓶颈，不称其主导端到端增益。
- 若 C 相比 B 只改善 TPOT：明确写成“关键资源细化在已测场景中主要改善解码间隔”，不声称吞吐和 TTFT 普遍获益。
- 若 C 在两种拓扑三种子上稳定改善多项指标：可以说存在一致的仿真增量，但 n=3 且一个种子参与调参，仍不称统计显著或跨拓扑泛化。

正式三种子实验及数据文件见 `EXPERIMENT_EXTENSION_PLAN.md` 和 `RUN_MANIFEST.json`。本文件先规定解释规则，结果完成后再填具体数值。
