# 1 引言（中文初稿）

在由不同型号 GPU 和跨区域链路组成的集群中，部署一个无法由单台设备完整容纳的大语言模型，需要将模型层分配到多台设备，并为每个请求选择覆盖全部层的执行路径。同一请求的各阶段必须依次完成，但多个请求又会争用 GPU、链路和 KV 缓存。因此，某条路径的性能既取决于其静态计算与传输代价，也取决于请求到达时资源上的未完成工作。面向这种异构环境，[HexGen](https://proceedings.mlr.press/v235/jiang24f.html) 展示了非对称模型划分的价值；[Helix](https://www.cs.cmu.edu/~rvinayak/papers/Helix_ASPLOS_2025_Serving_LLMs_over_Heterogeneous_GPUs_and_Network_via_Max_Flow.pdf) 则通过最大流与混合整数规划，联合设计模型放置和逐请求流水线。

现有方法已说明，放置和路由不能只按 GPU 算力或单条链路的带宽分别决定。Helix 的容量图刻画了异构 GPU 与网络对长期服务吞吐的共同限制，其在线调度在 KV 缓存容量约束下主要沿规划得到的流量份额选择路径；然而，容量相近的路径在请求到达时可能有不同的排队状态，固定份额也不能直接表示某个请求将遇到的等待。[Sun 等人](https://ece.iisc.ac.in/~parimal/papers/2025/peva.pdf) 已将等待、通信和计算代价纳入跨地域模型块服务的在线最短路，说明“考虑等待后选路”本身并非新的算法。对于异构 GPU 流水线，仍需回答一个更具体的问题：如何在放置阶段识别由计算与通信的先后关系、资源串行化共同形成的瓶颈，并让放置输出的合法路径结构与运行时的资源状态使用一致的代价视角？

这一问题的关键在于，**路径和瓶颈会相互改变**。例如，缩短某条路径的计算阶段，可能使更多请求汇入同一共享 GPU；增加路径选择也可能带来跨设备传输或 KV 缓存占用。只优化一条代表路径会低估多条可拼接路径汇合后的资源需求；只在部署后调整路由，则无法消除放置已经造成的昂贵层边界。我们据此提出 **RCAPS**（Resource Contention-Aware Placement and Scheduling）：在同一资源视角下，先判断哪些 GPU 和链路真正制约请求推进，再决定层放置及其可用路径，最后依据请求到达时的状态选路。

RCAPS 在离线阶段将计算、传输和等待表示为带有请求依赖与资源依赖的事件有向无环图，通过最长完成链及路径集合需求估计关键资源。放置器在显存容量和物理链路约束下，以**共享前缀和两条各自覆盖剩余模型层的后缀**构造初始层放置，并针对关键资源调整前缀边界、相邻层划分及设备顺序。这一结构是受约束的搜索起点；导出的层兼容图还包含满足层连续性和物理连接条件的跨后缀拼接边，因此在线请求并不限于两条固定路线。请求到达时，调度器读取 GPU、链路队列和活跃 KV 会话的当前状态，在层兼容图上以等待、传输及计算工作量为代价选择提示阶段路径；后续解码复用该路径，并合并同一链路上已经就绪的解码传输。离线放置采用启发式局部细化，不声称获得全局最优。

我们在 Helix 事件仿真器中，以相同拓扑、请求轨迹和固定测量窗口，将 RCAPS 与原版 Helix 的放置及最大流调度进行端到端配对比较。在单集群与三集群的官方负载下，三个种子的逐种子相对变化均值显示：RCAPS 的输出吞吐分别提高 **8.67%** 和 **18.85%**，P95 首 token 时延（TTFT）分别降低 **34.28%** 和 **54.26%**，P95 输出 token 间隔（TPOT）分别降低 **54.22%** 和 **70.06%**。这些数字描述的是**完整系统**相对 Helix 的仿真结果；单个组件的效果由固定放置或固定调度的受控实验另行评估。

本文的贡献概括如下：

1. 提出资源依赖事件图与路径集合需求模型，将请求的执行先后关系和 GPU、链路竞争共同估计关键资源需求，并通过仿真资源忙碌排序检验其解释能力。
2. 提出拓扑与容量约束下的共享前缀、双后缀放置及关键资源邻域细化方法，输出包含合法拼接边的层兼容图，在控制搜索规模的同时为在线调度保留路径选择空间。
3. 实现使用当前 GPU、链路和 KV 会话状态的分层图路由与已就绪解码传输合并，并在两种异构拓扑、成对请求轨迹上报告吞吐、尾延迟及组件归因。

上述证据目前限于两种已测拓扑的事件仿真；种子 1 曾参与开发调参，真实 GPU 与网络环境中的性能仍需进一步验证。
