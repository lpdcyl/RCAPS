# V3 M2 单边界复制分支的并行能力验证

本方案已执行。代码、冻结布局、65 个计划窗口的哈希审计（59 个完整结果、6 个 KV 容量断言）、论文图和结果解释见 [v3_m2_branch_parallelism](v3_m2_branch_parallelism/README.md) 与 [FINDINGS_CN.md](v3_m2_branch_parallelism/FINDINGS_CN.md)。探索性扫描之后另行声明了单集群 600 token/s 的独立种子补充窗口；正式预选的 700 token/s 单路径在 2/3 种子中触发 KV 容量断言，因此没有把失败窗口计作零吞吐。

## 要检验的主张

固定一个共享前缀和一个层边界，增加后段完整副本链，使请求能在更多独立分支上并行处理，从而提高可服务负载和高负载下的输出吞吐。这里不检验第二边界。M1 图构建规则、M3 代价与执行语义、物理池、请求轨迹及正式窗口保持一致。

Helix ILP 只作为外部放置基线。实际冻结布局并非零复制：80 层模型在 C1 单/三集群分别部署了 128/122 个层副本，部分层最多 3 份，完整合法路径为 9/5 条。不能把 Helix 行标为“无复制”。

## 实验 A：同一父布局，嵌套删减分支

选单边界 `1→3` 父布局，固定边界 48、共享前缀的 GPU 与层分配、保留分支的 GPU 链与层分配。从父布局完整删除后段分支，得到 `k=1,2,3` 条完整副本链。`k=1` 每层只有一份，是严格的单路径无复制基线。删除分支后重新导出部署，检查容量、KV、链路、源汇连通和完整路径。

| 资源池 | 父布局来源 | k=1/2/3 已验证合法时的启用 GPU 数 |
| --- | --- | --- |
| C1 单集群 | 候选库中的 `1→3`、边界 48、24 GPU 布局 | 11 / 18 / 24 |
| C1 三集群 | 冻结 V3 `1→3`、边界 48、23 GPU 布局 | 11 / 17 / 23 |

主机制实验在每个 `k` 下只开放对应副本链的**规范完整路径**，即分别 1、2、3 条路径；M3 在可用路径上仍执行同一实时打分。这样 DAG 中大量跨副本切换路径不会随 `k` 一起成为未经控制的变量。另以完整 V3 层兼容 DAG 对 `k=2,3` 重跑关键负载，检查机制能否迁移到论文主方法的实际路由空间。

分支优劣可能影响结果。主结果用预先固定的 GPU ID 顺序构造嵌套集合；在关键高负载下，对 `k=1` 的三个单分支选择和 `k=2` 的三个双分支组合全部复核，并报告范围，不能事后挑最好组合。

**预期若并行复制起作用：**低负载下各 `k` 吞吐接近目标输出到达率；负载升高时 `k=1` 最早出现后段队列增长和完成率下降，`k=2` 随后出现，`k=3` 最晚。多分支的总输出吞吐增加，后段工作分散到多个副本，共享前缀的负载基本不变。若共享前缀先饱和、`k` 增加后吞吐不升，就不能主张这组资源池的瓶颈由复制分支解除。

## 实验 B：相同 GPU 总数的结构对照

实验 A 的启用 GPU 数随分支增加，所以它证明“开放更多完整分支”的整体效果，还不足以排除“只因使用更多 GPU”。C1 单集群可做补充对照：固定边界 48、共享前缀 `[6,9,10,17]`、相同 24 个物理 GPU 和相同 M3；比较现有合法的 `1→2`（112 层副本）与候选库中预先按冻结完整静态目标选出的 `1→3`（144 层副本）。两组都启用 24 GPU，差别在于后段形成两条还是三条完整副本链及相应层分配。

该对照不能把“增加层副本数”从“增加分支数”中分离；更多完整层副本正是复制并行能力的物理实现。报告每个 GPU 的层数、型号、每段链长和链路负载，避免把资源重排隐藏在 `k` 标签后。三集群现有候选库没有同边界、同 23 GPU 的 `1→2` 候选，不强行声称已有等资源对照；需先做合法性搜索，再决定是否扩展。

## 负载、读数与论文判定

先用单种子探索性负载扫描找到各 `k` 的排队转折，再**冻结**正式负载点，并在所有变体上运行相同 0/1/2 种子、1800 秒、零预热、不排空窗口。现有 V3 单集群扫至 900、三集群扫至 400 offered token/s 仍没有明确吞吐平台，不能直接把这些上限称为容量。正式扫描需覆盖低负载、转折附近和高负载；若最高点仍未显示平台，只报告已测负载下的曲线和完成率，不报告精确最大容量。

主读数：输出 token/s、完成率、末端积压及其随时间的增长、共同完成请求的 P95 TTFT/TPOT。机制读数：共享前缀与每个后段分支的 GPU 忙碌比例、队列等待、处理 token 数、活跃会话/KV 占用；每条链路的忙碌与等待。现有候选正式 JSON 已记录 `gpu_busy_fraction`、`gpu_queue_request_s`、`link_occupied_fraction` 等，可复用同一埋点口径。固定窗口 P95 必须连同完成率和积压解释。

论文主图建议为同一拓扑下 `k=1/2/3` 的“负载—输出吞吐”与“负载—完成率/积压”曲线；副图展示共享前缀和后段分支的忙碌/排队分解。主表列 `k`、启用 GPU、层副本、关键负载的吞吐、完成率、积压和共同请求尾延迟。

只有当嵌套分支实验出现预期的负载 × `k` 顺序，且相同 GPU 数对照仍支持三分支时，才写“吞吐提升来自复制分支带来的并行服务能力”。若只在启用更多 GPU 时改善，应写“增加可用复制资源提高吞吐”；若高负载下共享前缀或链路先饱和，应按实测瓶颈收窄结论。三个种子只描述方向与波动，不做显著性声明。
