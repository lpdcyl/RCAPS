## 失败事实与诊断边界

失败窗口为 `single/load700/static/seed1`。进程 PID 55080 于 10:28:18 UTC 启动，10:30:31 UTC 被队列记录为失败，退出码 3221225477，即 **0xC0000005**。Windows Application Error 事件时间为 10:30:27 UTC，进程身份一致，故障模块为 unknown，偏移为 0。工作日志最后可见到模拟时间约 1004 秒，随后记录 `Windows fatal exception: access violation`；它不是一个完整的 1800 秒结果。

Python 栈停在 `model.py:get_inference_statistics` 的 `for request in requests`，经 GPU 执行、资源探针和分块事件处理进入。栈位置不足以确定根因，更不能据此认定分块逻辑、NumPy 或某一原生模块有错。原生崩溃绕过 Python 异常捕获，所以没有 `failure.json`；失败由原始 index、worker 日志和 Windows 事件共同保留。

只读系统检查发现：

- 近 7 天共 33 个 Python Application Error 事件，其中 32 个为 c0000005，另 1 个为 c0000409。涉及 base conda、gllm conda 和 Codex 自带 Python 三个运行路径；事件总数按路径为 18/13/2。不能将这些事件全部归为本项目实验。
- 本机为 Core i9-14900KF，BIOS M.80，日期 2025-04-10；Windows 注册表 `Update Revision` 字节为 `[44,1,0,0]`，按小端解码为 **0x12C**。
- 本次 WER 存有 Report.wer，未找到事件列出的临时 dump；缺少可用于原生栈、寄存器和内存分析的崩溃转储。

[Microsoft 对 c0000005 的说明](https://learn.microsoft.com/en-us/shows/inside/c0000005)仅将其定位为访问无效内存的异常类别，可能原因不唯一。[Intel 官方针对部分第 13/14 代桌面处理器的指引](https://www.intel.com/content/www/us/en/support/articles/000102331.html)建议 Intel Default Settings，以及包含 0x12F 或更新微码的最新 BIOS。当前主机记录与该建议有差距，值得优先排查，但**不能由此确认 CPU 已损坏、确认本次崩溃由硬件引起，或确认升级后就会解决问题**。历史 TypeError 的根因仍未解决，也没有证据证明它与本次原生崩溃同源。

## 如何呈现空间与时间两层控制

空间层是对可选路径边的静态稀疏准入，限制请求在兼容路径间过度分散，目标是保留批处理聚合；时间层是对慢计算链路上 Prompt 激活传输设置固定 4 MiB 分块，在块边界让出调度机会，目标是缩短连续占用。它们与 V3 实时资源感知路由并存，不能将“静态准入”写成“静态路由”。

三集群负载 320 的四格给出了直接证据：实际路径数均值 V3/仅空间/仅时间/V4 为 33/8/31/8；token 加权 Decode batch 为约 6.80/9.66/6.58/9.21；Decode 网络等待总量为约 7547/8013/2593/2778 秒。空间层改善聚合与 GPU 工作量，但单独使用时 TPOT 并不改善；时间层减少等待，合并后同时改善相对 V3 的延迟和工作量。占用重叠只是机制观测，不等于全部等待的因果分解。

以下百分比均先逐种子计算 `V4/对照−1` 再取三种子均值；不是均值之比，也不是统计显著性结论。

| 三集群 320 的对照 | V4 TPOT 变化 | V4 GPU 秒/token 变化 | 含义 |
|---|---:|---:|---|
| V3 | −13.39% | −27.36% | 完整系统的联合收益 |
| 规范图+4 MiB | −8.92% | +70.20% | 保留部分绕行以工作量换延迟，非最小工作量策略 |
| 全链路4 MiB | +0.78% | −0.55% | 慢链路选择不是该点延迟最优，差异较小 |
| 慢链路1 MiB | +5.40% | −2.71% | 固定4 MiB牺牲部分延迟以减少工作量 |
| 慢链路2 MiB | +4.40% | −2.77% | 同样体现折中 |
| 慢链路8 MiB | −3.57% | +0.90% | 更大块减少工作量但延迟更高 |

因此可写“空间聚合与时间让出的互补控制”，不宜写“4 MiB 最优”“只分慢链路全面优于全链路”或“显著超加性协同”。160 的交互项存在不同符号，且只有三个已知种子。固定 4 MiB 是预先冻结的折中，不能看到 1/2 MiB 结果后回改主方法或重新挑参数。

主曲线显示，单集群六个负载的 V4 TPOT 相对 V3 均值下降约 0.78%–12.73%，三集群下降约 2.50%–15.65%；GPU 工作量也下降，但部分负载 TTFT 上升。因此收益必须同时报告 TTFT、完成率、积压和共同完成请求对照，不能表述成所有指标一致改善。GPU 秒/token 是模拟忙碌工作量，不能直接称作实测节能。

## 恢复前提及剩余论文缺口

当前冻结协议规定任何进程崩溃停止新派发，并禁止自动重试；本轮据此中止。恢复需要用户先处理或确认运行主机：核对主板官方 BIOS/微码和 Intel 默认设置，或提供经验证的独立稳定主机。BIOS 更新、重启及硬件检查需由用户操作，不能由实验监控任务代为执行。随后单独登记诊断与恢复方案，保留当前失败及全部结果；任何复现失败的诊断运行都使用独立路径，不能覆盖正式失败窗口。改变主机或解释器需记录新环境身份和跨环境等价性，不能悄悄合并成原 manifest 的同一批结果。

剩余证据分两类：

1. **本次计划尚未闭合**：静态/实时路由 M3 和单边界/多阶段 M2 的两拓扑组件消融；C2/C3 的 V3–V4 三种子泛化；本次原生失败的诊断与恢复处置；可信环境下已完成结果的复核。精确 22 个未启动窗口见完整性审计，另有 1 个失败窗口需单独处置。
2. **本次 120 格原本不覆盖**：跨带宽/RTT、慢链路阈值、画像偏差、请求长度及到达突发性、窗口/预热设置的稳健性；异构资源和更大拓扑的外部有效性；真实运行时的传输让出、调度开销与尾部 token 延迟验证；若声称节能则需真实功率/能量测量。不能因当前批次或其未来补齐而声称所有稳健性和硬件实验完成。

在恢复条件明确之前，关闭自动跟进，避免对已终止队列持续空轮询。当前结论只支撑限定场景下的两层控制机制和性能折中，尚不足以宣告正式论文实验全部完成。
