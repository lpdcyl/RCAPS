# 少 GPU 的容量与路径联合优化

目标是在给定负载下，先满足 Helix 全池的输出吞吐、P95 首 token 延迟和 P95 每 token 延迟，再最小化所用物理 GPU 数。选卡数量是优化目标；三项性能是必须同时满足的约束。

## 离线布局

对每种机器、每种驻留层数，使用模型权重占用之后剩余显存所对应的 KV 容量，限制可放置层数。候选还要覆盖全部 80 层、满足物理连通性，并控制流水线跳数和静态瓶颈。容量充足但链路慢、流水线过长的布局也可能失败，所以静态分数只用于生成候选。

这里不能只要求“一条请求能放下”。高负载同时存在数百条会话，需要并发 KV 余量。400k/600k 表示每驻留层的最小 KV token 容量，属于布局参数，不是已经测出的吞吐能力。

## 在线准入与路由

对请求 q，令输入长度为 p，公开最大输出长度为 U=1000。在节点 i 实际执行 l 层，则预约量为 `(p + U) * l` 个 token-layer 单位。所有已准入请求在该节点的预约量之和不得超过节点 KV 容量。

路由动态规划只考虑还有足够预约容量的边，并利用已观察到的计算队列、链路队列和 Decode 会话成本选路。跨副本路径可能跳过部分驻留层；新方案只预约实际执行层，旧方案预约全部驻留层。模拟器也只为实际执行层分配 KV，因此新方案减少的是多余预约，仍覆盖输入及最大输出的完整生命周期。

Prompt 确定路径后，Decode 沿同一条路径运行；真正完成且实际 KV 释放后才归还预约。容量不足的请求在 source FIFO 等待，等待计入首 token 延迟。路由不读取未来真实输出长度，不丢弃请求。准入能避免容量断言；能否同时维持性能取决于布局和处理能力。

## 证据标准

42 个计算节点含 64 张物理 GPU。本轮三种候选分别使用 17/38、31/53、40/62 个节点/物理 GPU。

600 秒、seed 101 仅选型。通过后冻结候选，用 1800 秒、seed 0/1/2 与 Helix 原正式基线逐一配对。比较输入轨迹、负载、窗口、预热、到达数及集群哈希；每个种子的吞吐不低于 Helix、两项 P95 延迟不高于 Helix 才支持目标。同时报告完成率、首 token 覆盖和积压，保留所有失败窗口。

此前 22 节点/44 GPU 的三个正式窗口均未达标；31 节点/53 GPU 的全部驻留层预约在 600 秒筛选中吞吐较高但首 token 延迟恶化。新方案的实际结果见 RESULTS_CN.md，不能用设计上的容量安全代替性能证据。

## 600 秒筛选观察

按实际层预约后，31 节点/53 GPU 在同一 seed 101 轨迹达到 376.908 token/s、P95 TTFT 5.062 s、P95 TPOT 0.959 s；Helix 为 354.105、5.305、1.496。1347 条请求全部准入，没有源端容量等待。这是筛选通过，正式结论仍取决于三个 1800 秒窗口。

另外两个布局未通过。17 节点方案的共享 A100 节点 8 和 40，峰值预约均达到容量的 99.9997%；40 节点方案的共享 V100 节点 12 也达到 99.9997%。节点编号为 placement.json 中的编号，结果 JSON 中的模拟节点编号加 2。两个布局分别最多有 286 和 313 条请求在 source 等待。总卡数或统一的每层容量阈值无法表达共享段承载全部流量这一约束；后续布局搜索应将容量余量与各段承担的会话比例结合。
