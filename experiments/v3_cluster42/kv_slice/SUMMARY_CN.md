# 高负载少卡实验结论

本轮已完成：三个 600 秒选型窗口，以及冻结候选的三个 1800 秒正式窗口。相同 2150 offered token/s、相同种子、相同请求轨迹，均为 CPU 事件模拟。

31 个计算节点、53 张物理 GPU 的方案，相对 Helix 全池 42 个节点、64 张 GPU，减少 11 张卡（17.19%）。三个正式种子吞吐均提高 1.31%–1.76%，P95 每 token 延迟均降低 33.01%–34.39%。首 token 延迟两个种子改善，种子 0 增加约 24 毫秒（0.494%）。因此**尚未通过预先登记的“三个种子三项指标全部不劣于 Helix”严格目标**。

三个种子的指标均值为：吞吐 467.086 对 459.729（+1.60%）；首 token P95 的均值 4.922 对 5.071（−2.93%）；每 token P95 的均值 0.916 对 1.377（−33.48%）。这些是三个种子指标的算术均值，不是合并请求的 P95，也不作显著性结论；均值改善不替代逐种子严格判定。

## 改动及其作用

- 布局依据权重占用后的 KV 容量约束可驻留层数，并结合链路、流水线跳数和副本宽度生成候选。
- 路由按输入长度加公开输出上限 1000 token 为实际执行层预约完整生命周期 KV。跨副本路径跳过的驻留层无需预约。Decode 固定沿 Prompt 路径；实际 KV 释放后才释放预约。
- 容量不足的请求在 source FIFO 等待，等待计入首 token 延迟。不读取未来真实输出长度，不丢弃请求。

旧的 22 节点/44 GPU 方案三个长窗口均因准入排队而失败；同一个 31 节点布局按全部驻留层预约的 600 秒窗口首 token P95 为 10.756 秒。改为实际执行层预约后，该 600 秒窗口为 5.062 秒；三个正式窗口均全部准入、零容量延后、零 KV 断言。准入机制在当前正式负载下提供容量保护，但未产生等待；不能把本轮性能增益全部归因于准入。

首 token 覆盖分别为 3939/3942、3925/3933、3909/3915；Helix 为 3939/3942、3927/3933、3908/3915。完成率分别为 89.65%、89.35%、91.70%，均高于 Helix；末尾积压分别为 408、419、325，低于 Helix 的 476、489、400。完整表见 RESULTS_CN.md。

17 节点/38 GPU 与 40 节点/62 GPU 的候选均未通过选型。共享前段的 KV 预约接近饱和，导致源端等待；这说明布局必须考虑每段承载的会话比例，而不只看全池总显存。失败结果全部保留。

## 复现及适用范围

协议在正式运行前冻结于提交 `519fe66`。原始结果在 runs/，输入、布局、准入模式及物理卡数核对在 analysis.json。历史 Helix 集群文件为 LF 换行，本机检出为 CRLF；两种原始哈希已保留，按同一文件仅替换换行复算核对，Git 内容与原完成分支一致。模拟器、评估代码、物理集群及 Helix 布局未修改。

容量安全专项测试覆盖实际执行层的边界预约、真实 KVCache 增长到公开输出上限、占满拒绝和完成释放。数据集实际最大输出为 1000 token，与预约上限一致。结果只支持当前模型、集群、轨迹和负载下的模拟表现，未进行真实 GPU 部署，也不能证明 53 张 GPU 是最少数量。

下一步最值得解决的是共享段按会话比例约束容量，以及在新协议下优化首 token 尾延迟。种子 0 已用于正式判定，针对它调参后的复测应作为新实验，不能修改本轮阈值或覆盖结果。
