# 官方高负载三方案成对实验

LLaMA-70B、24 GPU，种子 0/1/2，单集群 700 token/s、三集群 320 token/s，
每次测量 1800 s，无预热，Gurobi 13。有完整结果的三方案在同场景同种子下，
`trace_sha256` 与到达请求数严格相同。

三方案依次为：Helix 放置＋Helix 调度；新放置＋Helix 调度；新放置＋新调度。
中间方案只更换放置，用于直接归因官方高负载下的放置效果。
如果原 Helix 在线调度在新放置下触发不可路由断言，该运行标为失败，
不使用截断窗口指标，也不把失败种子算作改善。

### 同参数重跑诊断

重跑在仿真时间 1194.046 s 再次触发同一断言。节点 0 的唯一下一跳是节点 8，流量份额 100%、prompt 上限 6144 token；本次 prompt 仅 409 token，所以流量与长度过滤均通过。
唯一失败项为 `Fail-KV`。Helix 预计本次请求需 (409 + 240×0.6)×12 = 6636 个 KV 单位；节点 8 当前预计空余 342312，加入后为 335676，低于其总容量 3377472 的 10% 保留量（337747.2）。在线模式遇到无可行下一跳便断言终止。

## 解读

三集群中，固定 Helix 调度仅更换放置使吞吐平均增加 15.56%（3/3 种子完成）；固定新放置再更换调度增加 2.85%。
新调度进一步降低 TPOT，但相对于中间方案的 TTFT 仅 1/3 种子改善。
单集群中间方案有 1/3 种子触发 Helix 在线路由断言；因此不能声称其在官方高负载下稳定可行，也不能把 2/3 完成种子的均值写成完整三种子归因。

原始记录及日志位于 `runs/seed*/{single,multi}/paper_*.{json,log}`。
本表使用固定窗口、未排空尾部请求的在线协议；具体绝对延迟
和完成率应连同窗口末积压一起解释。
