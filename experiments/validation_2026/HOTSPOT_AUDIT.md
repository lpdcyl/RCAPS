# 离线资源需求与在线热点：三种子复核

`hotspot_audit.py` 对已有 70B 运行做**事后诊断**。它重算当前布局的两种离线 GPU 需求分数，再与同一布局、同一种子 1800 秒运行记录的 GPU 忙碌率和排队 request-seconds 排名比较。所有相关系数均覆盖 24 张 GPU，并按并列名次计算 Spearman 系数。这里没有训练新预测器，也没有产生新放置或在线收益。

| 拓扑与布局 | 代表路径需求 vs 忙碌 | 代表路径需求 vs 排队 | 路径集合需求 vs 忙碌 | 路径集合需求 vs 排队 |
| --- | ---: | ---: | ---: | ---: |
| 单集群初始 | 0.621 | 0.596 | **0.833** | **0.824** |
| 单集群最终 | 0.342 | −0.045 | **0.799** | **0.648** |
| 三集群初始 | **0.740** | **0.471** | 0.670 | 0.437 |
| 三集群最终 | **0.801** | **0.587** | 0.756 | 0.487 |

表内数值是种子 0、1、2 的算术平均。代表路径需求是两个骨架中每张 GPU 的 `max(prefill_s / prompt_tokens, decode_s / decode_batch)` 之和；路径集合需求调用当前 `path_ensemble.measure`。离线两种分数预测的是**工作需求**，在线两列分别是时间占比与累计等待，并不具有相同单位。单集群最终布局采用路径集合模式；三集群采用代表路径模式。因此，当前实际使用模式对在线忙碌排名具有一定解释力，但对排队排名的对应关系较弱，尤其不能凭一个标签推断队列最热 GPU。

三集群最终布局中，代表路径分数的最高值为 0.006125 秒，**GPU 4、5、14、15、17、18、19 七张卡并列**。`TopologyModel.measure` 用 `max(demand, key=demand.get)` 返回第一个并列项，于是日志写成 `gpu:17`。它不是独占第一的预测。按并列名次，GPU 17 的离线排名为第 4；在线排队三个种子均为第 23，忙碌分别为第 20、20、19。它只出现在约 19.2%、16.7%、17.3% 的实际已分配路由上。初始布局中也有六张卡并列最高，GPU 17 的实际路由出现率约为 18.9%、17.8%、18.1%。

这些数据支持两个更窄的判断：一是当前需求分数未充分反映在线选路频率；二是需求高与实际等待高并不等价。它们**尚不能证明**哪一项（路径选择、批处理、请求长度或链路与 GPU 的相互作用）贡献最大，也不能证明换一个代理一定提高放置后的吞吐或尾延迟。特别是把三集群直接切到路径集合模式并非现成答案：在当前最终布局上，它对忙碌和排队的排序相关性均低于代表路径模式。

下一步如果以“在线队列感知的竞争预测”作为方法贡献，应在不读取评测种子在线画像的前提下，对候选布局预测路径使用概率、GPU/链路服务需求与等待，并分别检验：① 跨布局的排队排名和 Top-k 热点；② 相同局部搜索邻域与预算下的布局差异；③ 种子 0、1、2 的配对在线吞吐、TTFT、TPOT、完成率和积压。预测排名提高只是中间证据；最终在线性能才决定能否声称方法收益。

复现：`python -m experiments.validation_2026.hotspot_audit`。逐布局、逐种子数值及轨迹哈希见 [`hotspot_audit.json`](hotspot_audit.json)。
