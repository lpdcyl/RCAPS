## 去掉离线事件图和关键资源分析后还剩多少收益

无事件图方案保留同一个拓扑初始化、同一组合法局部移动、最多 16 步贪心改进和 RCAPS 在线调度。它只用两条独立完整路径的平均计算、传输与传播时间作为离线目标，不构造多请求事件图，也不计算关键资源或资源需求排名。

- 单集群相对 Helix：吞吐 **+7.28%**，p95 TTFT **−23.58%**，p95 TPOT **−51.65%**。完整 RCAPS 对应为 +8.67%、−34.28%、−54.23%。无事件图方案保留了约 83.95% 的吞吐增量、68.8% 的 TTFT 降幅和 95.28% 的 TPOT 降幅（逐种子比值平均）。完整事件图搜索相对无事件图方案，三个种子的吞吐都更高，TTFT 和 TPOT 都更低。
- 三集群相对 Helix：吞吐 **+18.76%**，p95 TTFT **−54.87%**，p95 TPOT **−70.32%**。完整 RCAPS 对应为 +18.85%、−54.27%、−70.07%。三个种子里，完整 RCAPS 对静态搜索的吞吐差为 +0.058、+0.118、−0.017 token/s；TTFT 与 TPOT 差值正负不一致。不能声称事件图在此拓扑稳定提高在线性能。

单集群静态搜索接受 0 步，输出的 `solution.ini` 与 `simulator_cluster.ini` 和仅拓扑布局逐项相同。种子 0 实际重跑后，请求哈希、吞吐、尾延迟、路由及画像一致；种子 1、2 按完全相同的仿真输入复用仅拓扑原始结果，`summary.json` 标记了复用来源。因此单集群静态方案的收益来自拓扑布局与保留的在线调度，不能归于静态搜索本身。

## A：关键资源引导的独立作用

完整邻域事件图搜索和关键资源引导搜索在两种拓扑导出**相同的最终布局**，三个种子的在线结果逐项相同。单集群候选评估数从 115 降到 68（减少 40.9%），本机一次重算放置耗时约从 1.60 秒降到 0.90 秒。三集群两者均评估 272 个候选，接受 10 步，耗时约 5.73 与 6.01 秒。耗时受同时运行的仿真影响，候选数更可靠。当前证据支持单集群的搜索开销节省，**不支持关键资源筛选带来独立的在线性能提升**。搜索实现和计数见 `planning_costs.py` 与 `placement_costs.json`。

## B：实测瓶颈与代理的差异

所有资源画像均在相同请求轨迹下被动记录；协议检查确认 12 组可与既有结果配对的运行，其吞吐、尾延迟、完成率、积压、路由和轨迹哈希均未因画像改变。

- 单集群从初始到完整放置，逐 GPU 排队累计值的三种子平均总和从约 76,660 降到 61,250 request-s；p95 TTFT 和 TPOT 也随之下降。这与减少队列热点的解释一致，但画像本身不能单独证明因果机制。
- 三集群从初始到完整放置，逐 GPU 排队累计值的平均总和约从 21,882 到 21,687 request-s；无事件图静态布局约为 21,055 request-s。三者都存在明显的 GPU 排队；每条已路由路径都跨物理地域，平均跨地域次数约 1.04–1.05。图中分别呈现链路待发送、带宽传输和传播时间。由于两种拓扑负载不同，这些数据只用于描述各自的瓶颈，不用于跨拓扑因果归因。
- 三集群离线代理日志始终记录 `gpu:17` 为 `bottleneck_resource`，它对应仿真器 `Compute-19`。复核发现最终布局中它与另外六张 GPU 的代表路径需求值**并列最高**，日志只返回遍历到的第一个并列项，不能解释为 GPU 17 独占第一。最终布局的实测 GPU 排队排名在三个种子中均为第 23，忙碌排名分别为第 20、20、19；它仅出现在约 17%～19% 的已分配路径中。离线需求与在线热点并非同一指标，应避免把代理标签直接称为实测瓶颈。并列排名及整体相关性见 [HOTSPOT_AUDIT.md](HOTSPOT_AUDIT.md)。

结论限于这两个 70B 拓扑、固定负载和三个种子；不宣称统计显著。与 Helix 的差值同时包含放置与在线调度差异，不能把全部收益归因于离线事件图。
