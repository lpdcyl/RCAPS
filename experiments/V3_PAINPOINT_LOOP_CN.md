# V3 痛点 → 改进动作 → 实验闭环（路径空间与 Decode 批凝聚）

本页汇总一轮"找痛点—提动作—用数据闭环"的工作。所有候选都放在独立实验目录，冻结的
`rcaps/v3/`、布局和已发布窗口均未改动。判定规则在看到对应结果前提交（git 历史可查）。

## 1. 痛点：完整 DAG 的路径灵活性在单集群反而有害

已有证据（[`v3_pathspace_ablation`](v3_pathspace_ablation/formal_report.md)）：同一冻结布局上，
完整 DAG 相对规范路径在单集群吞吐 −1.05 token/s、P95 TPOT +0.053 s（三种子方向一致），
三集群则吞吐 +0.75、TPOT −0.125 s。97% 的单集群请求跨副本，但这一现象此前没有机制解释，
审阅指南把它列为待回答问题 3。

## 2. 机制诊断：先证伪，再定位

| 假设 | 检验 | 结果 |
| --- | --- | --- |
| H1 跨副本让请求多经过 GPU，部分段跳被低估 | 已发布 `route_counts`；逐请求跳数记录；全周期定价干预 | 完整 DAG 平均多 0.48（单）/0.94（三）跳。但单集群同一窗口内 TPOT 与部分段跳数无关（0 跳 0.516 s，1 跳 0.508 s，2+ 跳 0.525 s）；把部分段跳从约 65% 压到 0.4% 后，正式窗口 TPOT 差距只缩小 12%。**H1 不是主因。** |
| H2 路径多样化打散 Decode 批 | 被动探针统计每次层执行携带的 Decode 请求数（种子 100，结果与无探针窗口逐项一致） | 单集群平均 Decode 批：完整 DAG 2.91，规范路径 5.58；单请求批占比 41.9% vs 20.8%；Decode 层执行次数 945k vs 516k；GPU 忙碌比例 0.562 vs 0.324，而吞吐更低。**H2 成立。** |
| 三集群为何仍受益 | 已发布窗口的链路占用 | 规范副本内部有跨集群慢链路（11→22、23→13 占用约 0.10）；完整 DAG 绕开后降到 0.013/0.021。收益来自绕开慢链路，而非多路径本身。 |

模拟器对单请求 Decode 批计 2 倍画像时间（[`v3_m3_calibration`](v3_m3_calibration/RESULTS_CN.md)），
GPU 按驻留层循环执行，因此路径越分散，同一层上同时到达的 Decode 越少，执行次数越多。
冻结 M3 代价把每个活跃会话都按单请求批定价，无法区分"加入已有批"与"新开一批"。

## 4. 可形成的创新点（按证据强度区分）

- **已证明（正式窗口 + 机制探针）**：路径空间的价值取决于瓶颈类型。GPU/批次受限时，
  路径多样化打散 Decode 批，使每个输出 token 的 GPU 工作量约增加 80%；网络受限时，
  灵活路径的作用是绕开慢链路。这解释了路径空间消融中两种拓扑的相反方向，
  且"多跳"假设已被直接证伪。
- **已通过预注册非劣效检验（正式种子 0/1/2）**：按物理瓶颈准入的 M1×M3 接口规则——
  保留规范副本以维持 Decode 批凝聚，仅在慢链路处开放绕行，无新参数。单集群 P95 TPOT
  约 −9.5%、吞吐 +0.7%；三集群在 +2% 边界内非劣（+1.81%），相对规范路径仍好 13.6%。
  正式窗口平均 Decode 批：单集群 6.5–6.9，三集群 5.2–5.4。
- **必须写明的边界**：三集群三个种子的 TPOT 都比冻结 V3 略差，结论只能是"非劣"，不能写成
  两种拓扑都改善；非劣效边界是在看到开发窗口之后、正式窗口之前设定的（git 提交
  f945372），原始开发判定保留在报告中。只有 C1 两拓扑、一种负载、三个种子，未做统计检验。
- **环境敏感性（新发现）**：同一冻结 V3 代码在 Python 3.10 与 3.13 下，单集群种子 0、2
  从首批请求起选路分叉（TPOT 变化 ≤ 0.002 s，TTFT 最多 0.094 s），三集群逐项相同。完整 DAG
  中同构副本路径代价近似相等，选路对浮点细节敏感；规范路径/门控准入窗口跨环境逐项相同。
  以本地复跑为对照，判定不变。
- **暂不应采用**：标量定价修补（候选 1、2）。一个系数无法同时适配两种瓶颈。

## 4b. 泛化检验（[`v3_gated_generalization`](v3_gated_generalization/RESULTS_CN.md)，协议 4da0e32 先于正式窗口提交）

冻结布局、不重新规划；对照为本环境同轨迹重跑的冻结 V3；种子 0/1/2，1800 秒；判定规则沿用 C1 的非劣效标准。

| 条件 | 准入 | P95 TPOT 相对 V3（逐种子） | 吞吐相对 | GPU 忙碌 V3→门控 | 平均 Decode 批 V3→门控 | 判定 |
| --- | --- | --- | ---: | --- | --- | --- |
| C2 @160（平坦） | = 规范路径 | −4.12 / +1.42 / +1.48% | +0.34% | 0.539→0.145 | 1.2→5.0 | 不通过（要求三种子均降） |
| C3 @400（平坦） | = 规范路径 | +0.05 / +0.28 / +0.65% | +0.01% | 0.405→0.272 | 3.8→5.9 | 不通过 |
| C1 三集群，慢链路 ×0.5 | 4 条绕行 | +1.86 / +2.58 / −1.71%（均值 +0.91%） | −0.01% | 0.232→0.165 | 4.3→6.3 | 非劣，通过 |
| C1 三集群，慢链路 ×2 | 4 条绕行 | −0.90 / −1.86 / −1.01%（均值 −1.26%） | +0.02% | 0.294→0.208 | 3.4→4.9 | 通过（三种子均降） |

结论边界：
- **慢链路拓扑上泛化成立**：带宽减半或加倍时门控准入都非劣；带宽越高，它相对完整 DAG 越有利
  （×0.5 +0.91%，×1 +1.81%，×2 −1.26%，后两者来自不同对照环境，只看方向）。
- **平坦资源池上"TPOT 降低"不泛化**：C2/C3 判定不通过。C3 只有 2 条副本、完整 DAG 也只用 4 条路径，
  两者几乎没有差别；C2 的 TPOT 方向不一致。
- **稳定泛化的是效率而非延迟**：在全部 6 个条件（含 C1）上，门控准入都把平均 Decode 批提高、
  GPU 忙碌比例降低（C2 降 73%），吞吐不降、完成率不降。只有 GPU 接近饱和时（C1 单集群 700
  token/s，V3 忙碌 0.64）这部分节省才转化为 TPOT 下降；C2 在 160 token/s 下 GPU 远未饱和，
  多余的 GPU 工作没有形成排队。这是由已有数据得出的解释，尚未用负载扫描直接验证。
- 因此论文主张应写为：门控准入在慢链路拓扑上非劣、在所有测试条件下显著减少 GPU 工作量；
  TPOT 改善只在 GPU 受限的 C1 单集群得到正式验证。

## 4c. 单请求 Decode 2 倍规则反事实（[`v3_batch1_counterfactual`](v3_batch1_counterfactual/RESULTS_CN.md)，协议 849f1ac 先于正式窗口提交）

在运行进程内关闭模拟器对单请求 Decode 批的 2 倍计时（`simulator/event_simulator/model.py:131–132`，源码未改），
其余不变；C1 单集群 @700、C2 @160，完整 DAG 冻结 V3 vs 门控准入，种子 0/1/2，1800 秒。

| 池 | GPU 秒/输出 token 门控 vs 完整 DAG：规则关（逐种子） | 规则开 | 保留比例 | 规则关时 P95 TPOT | 规则关时吞吐 |
| --- | --- | --- | ---: | --- | ---: |
| C1 单集群 | −44.4 / −45.6 / −44.8% | −46.0% | 98% | −3.5%（规则开时 −9.5%） | +0.26% |
| C2 | −67.0 / −64.6 / −65.1% | −73.2% | 90% | **+30.1%**（三种子 +26.8~+32.8%） | −1.23% |

- **预注册判定：效率主张成立。** 两个池每个种子的 GPU 节省都远超 20% 门槛，并保留了规则开时节省的 90–98%。
  批碎片化造成的 GPU 浪费主要来自更多、更小的层执行，而不是 2 倍规则。
- **延迟收益在很大程度上依赖 2 倍规则（不在判定内，但必须写明）**：
  - C1 单集群：门控的 P95 TPOT 优势从 −9.5% 缩到 −3.5%，方向仍一致。
  - C2：关闭规则后，完整 DAG 的 P95 TPOT 从约 0.58 s 降到约 0.44 s，门控仍约 0.57 s，
    门控反而高 30%，吞吐低 1.2%。GPU 有富余时，没有单请求惩罚，分散到多条路径的小批次延迟更低。
- 修订后的论文主张：门控准入**稳健地减少 GPU 工作量**（与模拟器 2 倍规则无关）；
  **TPOT 改善依赖单请求批的额外开销模型**，只在 GPU 受限且该开销存在时成立。
  2 倍规则是否符合真实 GPU 行为，需要实测或文献依据，不能由本仓库的模拟结果回答。

## 5. 下一步建议

1. 负载扫描：在 C2 上把负载提高到冻结 V3 的 GPU 忙碌接近 C1 单集群的水平，预注册检验
   "GPU 工作量节省在接近饱和时转化为 TPOT/吞吐改善"这一解释。
2. 三集群的剩余差距：完整 DAG 中门控未放行的边（如前段 4→各副本的慢边之外的分流）
   是否承担了负载分摊；可用逐边路由计数做诊断，而不是直接放宽阈值。
3. 把选路平局的确定性（固定平局顺序、避免浮点累加次序差异）作为工程修复单独验证。
