# 挑战三：队列感知的分层 DAG 路由与解码传输合并

## 论文叙事

挑战一的事件 DAG 区分 GPU、链路和排队对请求完成时间的影响；挑战二的图划分提供若干合法的层覆盖链。挑战三面对的是运行时状态：同一条链的排队随请求到达而变化，而且已有 KV 缓存使解码阶段不能随意迁移。因此，提示阶段到达时一次性选择路径，并让后续解码沿原路径运行。

仅改变入口选路还不够。Helix 的原调度器在一个链路调度事件中对每条链路发送一个请求。跨集群解码激活很小，多个就绪解码请求顺序经过同一链路时会重复承担传播时延。本方法将运行时选路与就绪解码请求的链路合并放在同一调度框架中。

## 图模型与算法

节点 `(l, v)` 表示请求已完成前 `l` 层，当前所在 GPU 为 `v`。若 GPU `u` 拥有从层 `l` 开始的一段连续层，且 `v` 到 `u` 有链路，则添加一条将层边界推进到 `r` 的有向边。边界严格增加，所以图是 DAG。给定到达时刻 `t` 的资源快照，边代价为

```text
GPU 当前未完成工作 + 链路当前未完成工作
+ 本请求的提示阶段计算与传输时间
+ 该 GPU 上活跃 KV 会话的一轮解码服务需求
```

所有项均用秒计量。单请求解码画像按照仿真器的 batch=1 倍时规则修正。按层边界的拓扑顺序做最短路动态规划；当前实现逐个检查可行前驱，计算量随状态数与转移数多项式增长，不遍历完整路径集合。提示阶段准入时登记所选链，后续 token 沿同一链执行。计算代价来自当前队列、设备画像和链路参数，不使用预测的未来请求或输出长度。

链路空闲时，将**已经就绪**且下一跳相同的解码请求放入同一个传输对象；提示请求单独传输，不等待未来请求凑批。对同链路的 `k` 个就绪解码请求，仿真器的顺序传输时间为 `kL + Σbᵢ/B`，合并后为 `L + Σbᵢ/B`，其中 `L` 是传播时延、`B` 是带宽。合并减少 `(k−1)L` 的链路占用；它不改变每个请求的模型层序或 KV 所在位置。

## 与 Helix 的关系及可验证主张

[Helix](https://arxiv.org/abs/2406.01566)用最大流决定异构 GPU 的容量分配及在线路径。本实现的在线路径由当前排队状态上的分层 DAG 最短路给出，链路发包在就绪解码请求间做即时合并。可验证的贡献是：在**相同模型放置、请求轨迹和固定测量窗口**中，这套调度能否同时改善吞吐、P95 TTFT 和 P95 TPOT。

结果只代表本仓库仿真器的单种子实验。传输合并收益依赖“一组请求只支付一次传播时延”的仿真模型；真实网络实现和更多种子负载需要后续验证。
