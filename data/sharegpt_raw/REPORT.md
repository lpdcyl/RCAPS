# ShareGPT 真实 Prompt 数据集与输出长度预测报告

生成日期：2026-09-21
数据根目录：`data/sharegpt_raw/`

---

## 1. 执行摘要

本报告回答了三个问题：

1. **能不能拿到 ShareGPT 的真实 prompt？** 能。已下载并落盘，且校验为 HF 原版逐字节一致。
2. **真实的 (prompt, output_length) 配对能不能建起来？** 能，得到 92,729 对，原始共 94,145 条对话。
3. **能不能用 prompt 预测输出长度？** **只能弱预测，不能精确预测。** 这是本报告最重要的结论。

核心量化结论（可部署特征，即请求到达时真实可见的信息）：

| 指标 | 数值 | 解读 |
|---|---|---|
| Spearman(pred, true) | **0.392** | 中等偏弱相关 |
| R² | **0.160** | 只解释 16% 方差 |
| MAE | **185.0** tokens | 真值均值 363.5，相当于 51% 相对误差 |
| 分档准确率（6档） | **0.395** | 最大单档占 37.1%，等于「永远猜中间档」 |
| 二分类 AUC（output>512） | **0.709** | 弱信号，但显著优于随机 |

**结论：输出长度不可由 prompt 精确预测。** 长度本质上由回答的语义内容决定，而 prompt 只暴露了很弱的意图线索。

## 2. 数据获取

### 2.1 网络路径的曲折

HuggingFace 直连全部失败，最终走通的是 **ModelScope 镜像**：

| 路径 | 结果 |
|---|---|
| `huggingface.co` | 超时 |
| `hf-mirror.com` 的 `api/` 端点 | 可用（仅元数据） |
| `hf-mirror.com` 的 `resolve/` 端点 | **302 跳转到 `cas-bridge.xethub.hf.co`，该域名被阻断** |
| `HF_HUB_DISABLE_XET=1` | **无效**，镜像自身仍 302 到 xet CDN |
| **`modelscope.cn`** | **可用，8.64 MB/s** |

关键校验：ModelScope 上的 `gliang1001/ShareGPT_V3_unfiltered_cleaned_split`
返回 `Content-Length: 672837942`，与 HF 原版 `672837942` **逐字节一致**，确认是同一份数据。

下载产出：`data/sharegpt_raw/ShareGPT_V3_unfiltered_cleaned_split.json`（672,837,942 字节）

### 2.2 数据结构

```
94,145 条对话，每条 {id, conversations: [{from, value}, ...]}
from 取值分布: gpt 367790, human 333941, system 212, chatgpt 95, bing 67, bard 28, user 18
```

**易踩的坑**：只有 58,827 / 94,145 条（62.5%）的首轮是 `human`，其余首轮是 `system`。
因此必须搜索**第一条非空 human**，不能假设 `conversations[0]` 就是 prompt。

### 2.3 与仓库内置 `Dataset.SharedGPT` 的差异（重要）

仓库自带 `simulator/trace_generator/length_data/shared_gpt_*.pkl`，但统计量与本次重建**明显不同**：

| 指标 | 本次重建（过滤前） | 仓库内置 | 
|---|---|---|
| 配对数 | 92,802 | 82,814 |
| avg input | 214.0 | 74.1 |
| avg output | 364.3 | 228.6 |
| max input | 241,402 | 1,023 |
| max output | 37,622 | 1,046 |

**原因判断**：原作者做了更激进的过滤（内置版本 `max_input=1023`、`max_output=1046` 是硬上限特征）。
作者很可能只保留单轮对话并把长度压在上限内。**本次重建保留的分布更接近真实长尾**，但对齐到内置口径
需要额外过滤，二者不可直接混用。

如需向内置口径对齐，`input<=1023 & output<=1046` 可保留 93.5%，此时 avg_input=86.3（接近 74.1），
但 avg_output 仍为 359.0（远高于 228.6）——说明**输出长度差异不是长度上限造成的，而是配对定义不同**。

### 2.4 异常值处理

发现 34 条 `input_len > 10,000`，其中 2 条超过 100,000：

| id | input_len | 成因 |
|---|---|---|
| `6E4LLxD_12` | 241,402 | 用户粘贴了 394,465 字符的 CSV 数据 |
| `X46zi4U_6` | 108,829 | 粘贴 388,296 字符文档 |
| `WFRnBkR_10` | 79,412 | 粘贴 310,103 字符法律提案全文 |

**这些是真实数据而非损坏**，但对长度预测毫无信号价值，却会主导平方误差。
采用上限 `input<=8192`、`output<=2048`，仅剔除 73 条（0.08%），保留 92,729 条。

## 3. 预测可行性实验

### 3.1 数据泄漏的处理

首轮训练得到 R²=0.316，但最重要的特征是 `raw_num_turns`（置换后 MAE +41.1）。
**这是数据泄漏**：它是整段对话的总消息数，在首轮请求到达时根本不可知。
一个服务系统只能看到 prompt。因此报告 R²=0.316 会**高估**真实可达能力。

据此做三组对照：

| 特征集 | 说明 |
|---|---|
| A 全部特征 | 含 `raw_num_turns`，**仅作上界参考** |
| B 可部署特征 | 仅 prompt 文本可知信息，**真实可用** |
| C 仅 input_len | 单特征参照 |

### 3.2 三元对照结果（5 折交叉验证，样本外预测）

| 特征集 | MAE | RMSE | R² | MedAE | ≤50% | ρ | 分档准确 | ±1档 |
|---|---|---|---|---|---|---|---|---|
| A 全部（含泄漏） | 164.8 | 214.1 | 0.3157 | 130.4 | 0.619 | 0.545 | 0.433 | 0.841 |
| **B 可部署** | **185.0** | **237.1** | **0.1605** | **152.0** | **0.565** | **0.392** | **0.395** | **0.812** |
| C 仅 input_len | 203.5 | 257.2 | 0.0117 | 174.1 | 0.525 | 0.116 | 0.371 | 0.790 |

- 去掉泄漏特征，MAE 从 164.8 退化到 185.0（**泄漏虚高了 20.2 tokens**）
- prompt 特征相比只用 input_len 只提升 18.5 tokens MAE

### 3.3 二分类检验：信号到底有没有？

把问题放宽成「输出是否超过某个阈值」，用 AUC 衡量：

| 任务 | 多特征 AUC | 仅 input_len AUC | 正例占比 |
|---|---|---|---|
| output > 128 | 0.735 | 0.482 | 0.801 |
| output > 256 | 0.700 | 0.482 | 0.611 |
| output > 512 | **0.709** | 0.530 | 0.240 |
| output > 1024 | 0.805 | 0.518 | 0.011 |

**关键发现**：仅用 `input_len` 做二分类，AUC 只有 0.48–0.53，**完全等于随机**。
但多特征能到 0.70–0.81。**说明信号不在「长度」里，而在「意图」里。**

### 3.4 最强特征排序（与 output_len 的 Spearman 相关）

| 特征 | 相关 | 含义 |
|---|---|---|
| `is_code_req` | **+0.133** | 请求涉及代码 → 输出更长 |
| `is_write` | **+0.122** | 请求写文章 → 输出更长 |
| `avg_word_len` | **+0.112** | 术语多 → 输出更长 |
| `n_question_marks` | **−0.103** | 问号多 → 输出更短 |
| `n_chars_nospace` | +0.084 | |
| `input_len` | **+0.066** | **几乎无关** |
| `is_bullet_req` | +0.048 | |

所有相关系数绝对值都 < 0.14，**这就是天花板所在**。

### 3.5 失效模式：预测被压向均值

| 真实档 | 样本数 | 真值均值 | 预测均值 | MAE | 偏差 |
|---|---|---|---|---|---|
| 1–64 | 10,290 | 29.4 | 290.4 | 261.1 | **+261.0** |
| 65–128 | 8,146 | 98.2 | 325.7 | 227.9 | +227.5 |
| 129–256 | 17,668 | 194.3 | 343.7 | 152.1 | +149.5 |
| 257–512 | 34,369 | 369.7 | 370.7 | 78.1 | +1.1 |
| 513–1024 | 21,218 | 722.5 | 413.6 | 309.7 | **−308.9** |
| >1024 | 1,038 | 1,097.6 | 452.5 | 645.0 | **−645.0** |

模型几乎只预测 290–450 这个区间，**对短输出严重高估、对长输出严重低估**。
这是「信号不足 + 平方损失」的典型表现，而不是调参能解决的问题。

## 4. 结论

### 4.1 直接回答

- **能拿到真实 prompt**：已下载，逐字节校验通过。
- **能建立真实配对**：92,729 对。
- **能预测输出长度，但精度不足以支撑精确决策**：R²=0.16，分档准确率等于常数预测。

### 4.2 为什么预测不了

输出长度由**回答的语义内容**决定，而 prompt 只暴露**很弱的意图线索**（最强相关 0.133）。
这不是模型不够强，而是信息论层面的上限——**如果一个模型能做到 R²=0.8，那意味着 prompt 里
已经包含了答案的长短信息，这在语言上显然不成立。**

### 4.3 对碳感知路由的建议（重要）

你后续要做碳感知请求调度，需要估算请求成本。基于本报告：

1. **不要用点预测做精确成本估算**，误差（MAE 185 tokens，真值均值 364）会直接污染路由决策。
2. **改用风险/分布视角**：
   - 预测分位数（P50/P90）而非点值，用鲁棒优化或 CVaR 处理不确定性；
   - 或者放弃逐请求预测，改用**在线自适应**：先按保守估计分配，随 decode 推进逐步修正。
3. **如果一定要用预测**，把它当**粗分类**用（AUC 0.71 是可用的），例如区分
   「代码/写作类长输出」与「问答类短输出」，而不是预测具体 token 数。
4. **`is_code_req` / `is_write` 这类意图特征是最有价值的输入**，不是输入长度。
